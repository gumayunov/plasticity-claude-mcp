# Plasticity Workbench: launch and recovery

## Installation and launch

Requirements: macOS on Apple Silicon, Plasticity 26.1.3 and Node.js 24.

```sh
npm install
npm run setup:codex
npm run start:plasticity
npm run start:workbench -- --lan
```

If Plasticity is already running without MCP access, the launcher leaves it and
all open documents untouched. Save your work first, quit the application, then
run `npm run start:plasticity` again.

The last command builds the web interface, picks the first active private IPv4 address and prints an address such as `http://192.168.1.20:4317`. Without `--lan` the server listens only on `127.0.0.1`. On the Mac, open the owner session with a separate command, `npm --workspace workbench run open:owner -- --lan`; if the server was started without `--lan`, omit the flag here as well. The command opens a browser with a secret in the URL fragment; the interface exchanges it for an HttpOnly cookie and immediately removes the fragment from the address bar. Do not share the owner link. The plain server address gives no access to projects.

`setup:codex` adds this repository's Git marketplace and installs the plugin with both MCP servers. After installation, open a new Codex chat. If you use Codex without the plugin, register the MCP servers directly:

```sh
codex mcp add plasticity -- npm --prefix "$PWD" start
codex mcp add plasticity-workbench -- npm --prefix "$PWD/workbench" run mcp
```

The second MCP server looks for the service on loopback and on local private IPv4 addresses by itself. If the service is not running, the MCP server starts it with `--lan` and stops the process it created when it exits. `WORKBENCH_ORIGIN` is needed only to override the address explicitly. The MCP server reads the local `owner-token` from the Workbench projects directory; the file is created with owner-only permissions and must stay on this Mac. If `WORKBENCH_PROJECTS_ROOT` is set, use the same value for the HTTP service, the MCP server and the browser-opening command.

## Working with a project

A project stores a monotonic revision, STEP versions, exact B-Rep measurements, tables, annotations, references, construction journal checkpoint snapshots and print jobs. The agent selects a project through `workbench_list_projects` or creates one through `workbench_create_project`, then reads `workbench_project_status` before every publication and passes the current `expectedRevision`. A revision conflict does not overwrite data. After a significant stage, the agent reads `plasticity_construction_journal` and stores the result through `workbench_publish_construction_journal`; these snapshots survive a restart of both MCP processes.

In the browser, the owner can create a project with the **Новый проект** ("New project") button. On a narrow screen, projects are available in a horizontal panel above the model. If the plain address is opened without an owner session, Workbench shows the command for signing in on the Mac; a tablet link gives access only to its own project.

Conversation with the agent happens only in Codex. Workbench accepts structured actions: numeric dimension fields, an annotation batch and a separate print approval. HTTP approve/submit are available only to the owner session or to an MCP server holding the owner token; even a tablet session with `edit` permission cannot start the printer. The `min`, `max` and `step` constraints and the integer type are checked in the browser and again on the server. The agent reads accepted changes through `workbench_get_feedback` or `workbench_wait_for_feedback`.

The model panel contains working view commands, orthographic front and top views, a Z section, fit to view, selection, hiding, isolation and per-body transparency. The button on a table row with `linkedEntities` selects the corresponding body or face; a selection in the model highlights the linked rows. When drawing over a body, Workbench stores the world point and the available B-Rep body/face ID, not only screen coordinates. The "Поделиться" ("Share") dialog on the Mac shows active one-time links and tablet sessions; the "Отозвать" ("Revoke") button immediately closes access for the selected session without manual database work.

The **Поделиться** ("Share") button creates a one-time link with `annotate` permission for 24 hours. Open it on a tablet on the same Wi‑Fi network. The code is removed from the address bar after it is exchanged for an HttpOnly cookie. Pen, marker, arrow, point, text note and dimension stay visible over the selected model version and are saved as a local IndexedDB draft until the user presses **Передать изменения агенту** ("Send changes to the agent"). A dimension annotation is accepted only as a number with a unit; a mistaken last item can be deleted before sending. When the version is switched, Workbench loads a separate draft and shows only the submitted annotations that belong to that version.

The viewer tessellates STEP in a separate Web Worker. All cursor dimensions and mesh bounds are treated as approximate. Tables with the `native-brep` source contain Plasticity reference values. If a new STEP fails, the previous version stays visible.

Before publishing a version, the agent exports STEP into the project's `workspacePath` and calls `workbench_upload_project_artifact` with a relative path. The tool accepts only regular files inside that directory, rejects escapes through `..` and symlinks, determines the type from an allowed extension and sends the bytes to the server. The HTTP API still does not accept a path to a local file.

A reference is registered only after the agent has checked it. `workbench_register_reference` accepts a URL and/or an artifact already uploaded to the project, a license, a source class, the role `locked-reference` or `functional-envelope`, and a dimension table. A dimension without a reliable value gets `measurement-required`; critical rows stay visible until the user enters a value. Workbench is not an internet downloader and does not open URLs from the record.

## Print preparation and start

On this Mac, the official Creality Print 7.2.2.5483 arm64 was verified with the `Creality K1C 0.4 nozzle` and `0.20mm Standard` profiles. Workbench lists the filament profiles compatible with the selected machine separately; a live catalog check confirmed Creality `CR-PLA` and `Hyper PLA` alongside Generic PLA. The profile choice describes slicer settings and does not qualify the mechanical properties of the spool. The installed Intel-only `/Applications/Creality Print.app` is kept unchanged; on Apple Silicon, Workbench automatically prefers `/Applications/Creality Print (Apple Silicon).app`. For a different path, set `CREALITY_PRINT_EXECUTABLE` and `CREALITY_PRINT_RESOURCES_ROOT` (the `Contents/Resources` folder) in the Workbench environment. The Creality Print 7.2 CLI does not import STEP: the agent keeps STEP as the editable source and exports a separate binary STL in millimeters from Plasticity through `plasticity_export_stl`. The live route Plasticity 26.1.3 → STL → CLI produced 25 layers and real toolpath extents of 20 × 10 × 5 mm. The CLI imports and measures a 3MF of the same test Solid but ends slicing with an error, so 3MF cannot be treated as a supported Creality Print input. The slicer accepts only STL, OBJ or AMF verified for the adapter. The derived mesh, the profiles and a separate CLI `--datadir` are copied into the directory of the specific job; shared slicer settings are not changed. The result stores the SHA-256 of the STL and the G-code, toolpath extents, layer count, filament mass and estimated time.

If the G-code has no slicer-reported extents or object metadata, Workbench estimates the bounds from extrusion moves. For arcs in the XY plane, the extreme points of G2/G3 with I/J or signed R are taken into account; for an unknown or unsupported arc command the whole estimate is rejected, so that an overrun of the bed is not missed. This is a toolpath estimate, not a check that the selected printer firmware can execute this G-code dialect.

The full path is also checked through an isolated HTTP service and a real stdio Workbench MCP server: the MCP server creates a project, attaches an STL, selects the discovered profile, runs `workbench_assess_printability` and calls `workbench_slice_model`. In `--plasticity-target` mode, the acceptance run connects to an explicitly selected empty Plasticity document, creates a test Solid, applies exactly the Workbench DFM orientation (or confirms that the model is already aligned), compares the B-Rep with the STL and slices the export. The `--split-native` flag requires an explicit `--split-joint flat|alignment-pins|tongue-and-groove|dovetail`; it takes a deliberately oversized model, sets a 5 mm margin from the bed edge, calls the native split by the recommended usable volume and, when alignment-pins, tongue-and-groove or dovetail is selected, builds the corresponding native mating joint on every detected adjacent body pair through the public Plasticity MCP recipe. After that, the acceptance run checks the exact bodies, volumetric overlap between neighbors, separate STL files and batch slicing through a single `workbench_slice_parts` call. The joint dimensions and the 0.2 mm clearance in this fixed test scene serve only to check the mechanism and are neither a production recommendation nor a strength test result. Each G-code preview is read from the project asset endpoint and checked against the bounds; `workbench_submit_approved_print` attempts without approval are rejected, jobs stay `ready`, and the printer adapter is not called. The Plasticity acceptance run restores the original empty scene, and cleanup undoes changes only if the document and revision are unchanged. The plain K1C orientation produced a ready job with 25 layers after a `[0,0,21.9]` rotation; the native split with two test-fixture tongue-and-groove joints produced three separate bodies and three ready jobs. Orientation command: `npm run accept:workbench-creality-mcp -- --plasticity-target EXPLICIT_WINDOW_ID --output NEW_DIRECTORY --executable /path/to/CrealityPrint --resources-root /path/to/Contents/Resources`; add `--split-native --split-joint dovetail` for the full test of joined parts. For a ready-made STL, use `--input PLASTICITY_EXPORT.stl` instead of a Plasticity target. Add `--batch-parts 2` for a live check of two identical batch items. Evidence: `/tmp/plasticity-mcp-output`; native split joints: `/tmp/plasticity-mcp-output`, `/tmp/plasticity-mcp-output`, `/tmp/plasticity-mcp-output`; batch: `/tmp/plasticity-mcp-output`.

For a split model, export each separate part from Plasticity to its own STL, attach all STL files through `workbench_upload_project_artifact`, then call `workbench_slice_parts` with a unique label for each part, its SHA-256, reference extents and one selected profile. The service first checks the whole batch (2–32 parts), the revision, the profiles, the file attachments and DFM; only then does it create an independent slicer job for each part. A failed slice of one part is reported separately and does not hide the results of the others. Each ready part keeps its own G-code and its own approval in Workbench. Batch slicing neither approves nor starts printing.

The **Подготовка к печати** ("Print preparation") screen shows the DFM checks and the toolpath of the selected layer. The approval button lists the exact hash, printer, material and profile. The approval is also bound to the exact set of warnings and the time and material estimates. It only allows the agent to call `workbench_submit_approved_print`. If the model, project, profile, warnings or estimates change, the approval becomes invalid. On a timeout, the submission moves to `unknown`; the agent calls `workbench_reconcile_print_submission`, which only reads `print_stats` and the G-code list on the printer. The exact file in the current job means `submitted`. A file that is only in storage leaves the state `unknown`, so that it is not started twice. Only a confirmed absence of the file returns the state to `approved`; resubmission remains a separate call.

`workbench_printer_status` is read-only. For a discovered K1C, the local Moonraker on port 7125 is used. The state is taken from `print_stats`, so Klippy `ready` does not mask a print that is already running. Submission is allowed only in `standby`, `complete` or `cancelled`. Neither the status check nor slicing uploads a file to the printer.

The stock K1C firmware rejects a regular upload through its fork of `/server/files/upload`. The K1 adapter therefore follows the contract of the installed Creality Print: a single binary multipart file is sent to `http://<printer>/upload/<ascii-name>`, and after a successful write the exact name is started through Moonraker `/printer/print/start`. The name is limited to a short ASCII slug, the job ID and part of the SHA-256; for a fully localized title, the `plasticity` prefix is used. A live test confirmed upload and start of the file `80-40-8-e815d11e-9c113a5c8615.gcode` on the K1C. Regular Moonraker printers keep the standard `/server/files/upload`.

To change the printer, the agent first calls `workbench_manufacturing_profiles` with the `slicer`, `printerVendor`, `printerModel`, `material` and/or `nozzleDiameterMm` filters. The output is limited to 20 profiles by default and supports `offset`/`limit` (at most 100 per page), so a large catalog does not bloat the Codex context. For a found profile, the MCP server passes `printer.id`, `material.id` and `slicer.id` to `workbench_register_manufacturing_profile`; Workbench resolves them to the single match in the installed catalog, copies the machine/process/filament JSON into `.manufacturing-profiles` and computes the SHA-256 of each file. The agent neither needs nor receives local paths. For a user or imported preset, the full profile can be passed through the local MCP server; Workbench stores it as a separate record. The `draft`, `imported`, `official` or `user-verified` status stays explicit. The MCP server returns a safe description of the registered profile and an immutable `profileHash`; for the DFM assessment, `workbench_slice_model` and `workbench_slice_parts`, the agent passes this hash, and Workbench itself resolves it to the stored configuration. If the profile contains these settings, the catalog returns `nominalInfillPercent`, `sparseInfillPattern`, `wallLoops`, `topShellLayers` and `bottomShellLayers`; these are the preset's original global values and may differ from a job with a per-object modifier. Together with `material.nozzleTemperatureC` and `slicer.layerHeightMm`, this helps tie a coupon to the selected process, but it does not replace the actual record of the test temperature/orientation/settings. If the layer schedule from the G-code is complete, `workbench_slicer_interface_heights` returns only the requested interface numbers, the actual deposition Z and a ready `relativeOffsetMm` from the first layer, together with the job/profile/G-code hashes. The agent passes these offsets to `plasticity_plan_cohesive_layer_planes` without manual subtraction; the whole schedule does not enter the context. To check toolpath directions on all layers, including the last one, `workbench_slicer_layer_path_orientations` returns the selected indices in chunks of up to 32, together with the actual deposition Z and the same job and G-code hashes; incomplete coverage of arc moves stays explicitly flagged. The manufacturer name and model are kept as given in the source: the contract allows third-party printers, and whether a separate slicing or submission adapter exists is checked independently. A profile contains the material and nozzle diameter, quality, supports, shrinkage scale, hole compensation, verified assembly clearance, part purpose and expected load. Slicing accepts only a profile that fully matches the discovered or registered copy. On this Mac, live Workbench MCP checks passed for the Creality K1C through Creality Print and OrcaSlicer; the results stayed `ready` until a separate approval.

If the model does not fit, `workbench_assess_printability` checks axis-aligned and diagonal orientations. Its `rotationDeg` and `sizeMm` refer to the checked model revision. For a single Solid or a rigid group of Solids, the agent passes all exact IDs to `plasticity_orient_bodies_for_print` together with the same `expectedSizeMm`. The MCP server checks the prediction before changing the scene, rotates the whole group about the center of the combined B-Rep bounds in one history step and measures the new combined Plasticity extents with a 0.01 mm tolerance. After that, the assessment and slicing must be run again; a successful CAD check does not prove that the model fits in the slicer. If orientation is not enough, the response contains `splitPlan`: the usable bed volume including the margin, the computed grid of parts, the cut plane offsets, joint options and the required clearance. After applying the orientation, call DFM again in the coordinates of the oriented model. If a strength analysis or the user has marked a protected region, pass it as `split.protectedZones` with the exact source ID, axis and bounds relative to the minimum B-Rep bound. The result warns if a balanced cut crosses such a band. The agent can propose a full set of `split.cutOffsetsMm`; DFM checks the number of cuts, the bounds and the maximum size of each segment. The zone source is supplied by the caller: Workbench does not check that the ID belongs to a current strength analysis, and the absence of a conflict does not prove that the joint is safe. The `plasticity_split_solid_to_build_volume` tool accepts a single Solid; for an assembly, keep the relative placement of the components and split only the individual bodies that need it. The MCP server derives the segmentation and cut coordinates directly from the exact B-Rep bounds, creates and deletes temporary cutters, requires two valid closed Solids for each cut and checks the total volume and extents of all parts. For a non-standard seam, `plasticity_split_solid_by_plane` and `plasticity_split_solid_by_planes` are available. The parts are checked against the build volume again and exported/sliced separately. A joint is added by a separate call only after its type and a verified clearance have been chosen; the absence of volumetric overlap by itself does not prove physical assemblability or print tolerance. After a partially completed split, the agent reconciles the scene and the journal and does not repeat the command automatically. Even with a successful preliminary assessment, a job is created only if the G-code contains checkable bounds that fit within the build volume with a 0.01 mm tolerance.

## Recovery

- After a CDP loss or a timeout, call `plasticity_reconcile`; do not repeat a mutating command automatically.
- After an uncertain printer submission, call `workbench_reconcile_print_submission`. It does not upload, delete or start G-code.
- After a revision conflict, reread the project, show the new server values next to the draft and resubmit it only on an explicit action.
- Annotations on an old version stay with it with the `required` status; they must not be silently carried over to the new topology.
- For a backup, stop Workbench and copy the `.plasticity-workbench/projects` directory, including `workbench.sqlite`, WAL/SHM, `.artifacts`, `.manufacturing-profiles` and the private `owner-token`. Keep owner-only access permissions for the token.
- A link or an active tablet session can be revoked in the **Поделиться** ("Share") dialog on the Mac. A revoked HttpOnly token immediately stops passing project authorization.

SIGINT or SIGTERM close the WebSocket connections, the HTTP server and SQLite. Model and artifact files are not deleted.
